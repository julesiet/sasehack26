| R-01 | Major | `aidlc/spaces/default/intents/260919-agent-playground/inception/domain-design/components.md` > `external_dependencies` entry "Kasama API — POST /conversation/turn" | The catalogue models the call to `apps/api`'s `POST /conversation/turn` endpoint as an `external_dependency` (`kind: other`). But per `component-inventory.md`, `@kasama/api` is not infrastructure or a third-party service — it is an existing, code-you-write logical component in this same system ("service (HTTP API)"), and `architecture.md`/`decisions.md` themselves describe it as a "long-running API server," a lifecycle peer, not a dependency of the same kind as a database or SaaS API. The stage definition's own component-vs-infrastructure line ("Databases, caches, queues, and third-party services are `external_dependencies`... Infrastructure... never components") is written to distinguish infra from components — it was not meant to also swallow an existing, already-cataloged internal component just because this stage's brownfield scope only re-catalogues *new* building blocks. Filing `@kasama/api` as `external_dependencies` sidesteps the well-formedness rule that any named component/`owned_by` must be declared, and could mislead Units Generation (which decides deployment topology from this catalogue) into treating the existing API service as outside the system's component graph rather than as an existing component `PlaygroundCli` calls into. | Either (a) add a minimal `depends_on` entry pointing at the existing `@kasama/api` service (declared as an existing, out-of-scope-for-this-stage component, consistent with how brownfield stages elsewhere reference existing components by name) so the dependency edge is real and traceable, or (b) explicitly note in the Rationale/ADR that `external_dependencies` is being deliberately widened here to also cover "existing, unchanged internal services this stage does not re-catalogue," so the modeling choice is stated rather than implicit. Either fix is small; this does not block the current gate but should be resolved before Units Generation consumes this catalogue. | New |
| R-02 | Minor | `aidlc/spaces/default/intents/260919-agent-playground/inception/domain-design/components.md` > Component Diagram | The stage definition says the Component Diagram should have "one node per component, one labelled edge per `depends_on`" — but `depends_on` is `[]` in the machine-readable catalogue, so per that rule the diagram should have no edges. The mermaid diagram instead draws an edge from `PlaygroundCli` to a non-cataloged "API" node representing the `external_dependencies` entry. This is a natural and helpful thing to show for a reader, but it is not what Part B's stated derivation rule (diagram derived strictly from the catalogue's `depends_on`) actually produces, and it's the visual symptom of the same categorization choice flagged in R-01. | If R-01 is resolved by adding a real `depends_on` entry, the diagram becomes consistent automatically. If R-01 is instead resolved by documenting the widened `external_dependencies` scope, add a one-line note by the diagram (or in Rationale) that the edge shown represents an external dependency, not a `depends_on` component edge, so the diagram's derivation rule is stated rather than silently bent. | New |
